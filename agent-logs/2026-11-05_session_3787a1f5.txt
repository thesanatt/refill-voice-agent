⏺ The research is finished, and nothing in it is revolutionary for this build.
  I'd propose a carefully done standard pipeline: speech-to-text, LLM and
  text-to-speech on Pipecat. A plain code module works out the next step from
  database fields, and code, not the model, writes every sentence containing a
  drug, pharmacy, plan or price. Nothing is decided yet, and CLAUDE.md and
  docs/DECISIONS.md are unchanged.

  Why a pipeline: the reason is control, not accuracy. In EVA-Bench the best
  pipeline scored 0.504 against 0.467 for the best speech-to-speech model, which
  is roughly level. A text stage lets code fix the exact words before they're
  spoken, and the same core can run the SMS thread.

  Latency

  The 1 second target isn't met on turns where an LLM reads the reply. These
  figures are arithmetic from published numbers; nothing has been timed on this
  project.

  The largest input, 640 ms of LLM time, is a Haiku 4.5 stand-in, because no
  independent figures exist for Haiku 5.5 in voice. No independent source shows
  any system reliably under 1 s on a tool turn.

  What decides the call for a real patient

  - Date of birth: this is the riskiest field. Nobody has published a
    spoken-date test on any provider, and dateparser returns nothing for your
    exact CLAUDE.md example. Older speakers also pause more, so the turn should
    stay open until a full date parses, though that idea is untested.
  - Choosing a drug: only 22% of 99 patients aged 65+ could name their drugs
    from memory (Jones et al.). The agent should read the list with each drug's
    purpose and accept "the blood pressure one". It also needs a "not on your
    list" outcome, because fuzzy matching scored lovastatin, a different drug,
    82 against Atorvastatin.
  - Reaching a person: being trapped is the complaint that keeps recurring, so
    "speak to a pharmacist" has to work, even if only as a logged callback.
  - Dropped calls: a closed tab took about 30 s to reach the server, and a
    pagehide handler cut that to about 5 ms. That was a small test on plain
    aiortc, not Pipecat, and it ran in your persistent Chrome on localhost.

  Where I'd change the report

  1. Fast reader: the report says code must read clear answers to hit the
     target. I'd wait for timings: it would keep most happy-path turns away from
     the LLM, which weakens the agent loop reviewers want to see. The kickoff
     bar is no multi-second pauses, which 1.4 s clears at the median, though the
     slow end (up to 2.7 s) may not.
  2. Latency target: its new wording (under 1.5 s on LLM turns) moves the bar to
     fit an estimate. Define the measurement now, and change the number only
     after timing.
  3. Date of birth retry: keep what the kickoff approved, asking for the date
     again. The report's neutral re-ask of both fields gains little with one
     patient.
  4. First texts: three of them say "Reply YES" instead of asking the next
     question, which departs from CLAUDE.md and adds a turn. I'd ask directly
     and keep only the copay out of the first text.
  5. Timing test: also count tool calls written as plain text, because this
     design would speak them aloud. Anthropic documents this failure on Opus 5
     with thinking off; whether it affects Haiku 5.5 is unknown.

  Edge cases now covered in D6

  - Talking over: the agent stops as soon as the patient really speaks, but
    keeps going through "mm-hm" or "okay". If it starts too early, the two
    pieces of speech are read as one turn. Saved answers always stand, whatever
    gets interrupted.
  - Questions back: it answers from the record, then repeats its pending
    question. A price question before insurance is confirmed gets "as soon as we
    confirm your insurance", with no number. Medical questions go to a
    pharmacist, and emergency language gets a fixed 911 line.
  - Early or combined answers: one LLM pass can fill several fields, and the
    next line comes from the final state. Anything said before verification
    isn't stored, but is used afterward so the patient isn't asked twice. A
    half-finished date doesn't count as a failed attempt.
  - Protecting data: the patient comes from the session, never a tool argument,
    and no tool can list or search patients. The model never sees the stored
    date of birth, full member ID or copay table. "I'm the pharmacist" changes
    nothing, because no tool can act on it.
  - Other realistic cases: repeat requests, "hold on", "text me instead", a drug
    not on the list, an unknown pharmacy, a "no" at the end, and service
    failures. A speech service failure counts as a dropped call, so SMS takes
    over.
